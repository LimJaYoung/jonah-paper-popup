# 열려라 성경동화 — 순서대로 만드는 제작 지침

버전 3.2.6 · 2026-10-18 · 적용: 새 동화 / 기존 동화 수정 / 작업 재개

**먼저 읽고, 현재 단계를 확인하고, 그 단계의 결과를 검수한 다음 넘어간다.**

이 문서가 제작 순서의 기준이다. 전문 문서는 작업 방법을, 작품 기록은 현재 어디까지 끝났는지 설명한다. 오래된 메모를 임의로 조합하지 않는다. 이 지침은 작업 절차이며, 모든 단계를 자동 차단하는 프로그램이 구현됐다는 뜻은 아니다.

## 1. 우리가 만드는 것

모든 성경동화는 어린이가 이해할 수 있는 한국어판(ko)과 영어판(en)을 각각 제작한다. 하나의 제작소·작품 안에서 공통 장면과 자산을 관리하며 프로젝트를 언어별로 복제하지 않는다. 그림·캐릭터·종이 오브젝트·팝업 구조·장면 ID와 순서는 공유한다. 제목·화면 글자·나레이션·대사·자막·음성·동작 시점·장면 길이는 언어별로 관리한다. 기존 아동용 종이 팝업북 디자인·연출 규칙은 두 언어에 동일하게 적용한다. 책 위에서 종이 인물과 배경이 움직이는 팝업북이며, 영상은 재생 한 번으로 끝까지 자연스럽게 이어진다. 성경에 근거한 쉬운 말, 수작업 종이 질감, 책과 함께 접히고 펼쳐지는 구조를 지킨다.

브랜드는 **열려라 성경동화**, 한국어 제작자 표기는 **제작 · J.영**이다. 영어판도 승인된 로고·타이틀 원화·제작자 J.영 표기와 위치를 재사용한다. 영어 대본·자막·음성과 필요한 타이밍만 분리하며, 별도 영문 제목·브랜드 시안은 사용자 승인 전 기존 원화에 적용하지 않는다. 작품 제목은 성경 인물과 사건을 알아볼 수 있게 쓴다. 책의 위치·크기·카메라는 고정한다. 시선 이동, 클로즈업, 카메라 추적, 화면 회전으로 연출하지 않는다.

## 2. 시작할 때 읽는 순서

모든 세션은 [디자인·애니메이션 공통 기준과 시각 참고](DESIGN_ANIMATION_PROTOCOL.md)를 필수로 읽고 승인 이미지와 실제 구현 캡처를 직접 연다. 관찰한 특징 3개·유지 요소·변경 범위를 기록한 뒤 아래 순서를 따른다.

### 최상위 업무 분담 · 맥북과 집 서버 PC

**맥북의 이 대화에서 Codex가 영어 대본·영어 음성 생성·웹 제작소 연결·자막과 장면 타이밍 검수까지 담당한다. 집 서버 PC는 완성된 영어 입력으로 MP4 제작·출력 검수·유튜브 비공개 업로드를 담당한다. 한국어 완료 음성은 보존하며, Public 공개는 사용자 최종 승인 후에만 진행한다.**

| 담당 | 맡는 일 | 지켜야 할 경계 |
|---|---|---|
| 맥북 (MAC) | 한국어·영어 대본·번역·화면 문구, 원화·디자인·장면 구성·팝업북 연출·애니메이션, 영어 음성 생성·실측·웹 연결·자막/장면 타이밍 검수, 웹제작소 편집·저장 UI | 한영 원본을 검토·확정하고 승인 버전을 PC에 전달한다. PC 자동화 코드를 승인 없이 변경하지 않는다. |
| 집 서버 PC (PC) | API·자동화 엔진, 별도 승인된 한국어 음성·타이밍 작업, 맥북에서 완성한 영어 음성·타임라인을 사용하는 렌더링·자동 검수·MP4 출력, 유튜브 비공개 업로드·상태 기록 | 영어 번역·대본·디자인·원본 장면 연출은 직접 고치지 않는다. 원본 변경은 맥북에 요청한다. |
| 사용자 | 원본·결과 검토, 한국어·영어 최종 영상 각각 승인, 유튜브 공개 여부 최종 결정 | 비공개 업로드와 Public 공개를 구분한다. Public은 09~11의 언어별 승인·직접 공개 클릭 조건을 따른다. |
| 공유 승인 대상 | 공통 API·데이터 구조·공통 재생 연결·제작 지침·배포 설정 | 양측 승인과 지정 작업자를 확인한 뒤 변경한다. 파일별 소유권이 불명확하거나 미등록이면 수정하지 않는다. |

1. 한국어 완성 확정 후 **맥북이 영어 버전의 번역·대사·화면 문구를 제작·검토**한다. **영어 음성 생성·웹 연결·자막과 장면 타이밍 검수도 맥북의 이 대화에서 Codex가 직접 담당**한다. PC에는 완성된 영어 음성·타임라인을 MP4 제작·출력 검수·업로드 입력으로 전달한다. 영어 음성 제작을 PC 담당으로 다시 넘기지 않는다.
2. 단순 저장은 제작 승인과 다르다. PC는 작품·언어·장면/발화 ID·revision·원본 해시와 승인 근거가 있는 버전을 읽기 전용 입력으로 사용한다. 필드 이름과 실제 연동 지원은 코드·계약을 확인하며 추측하지 않는다.
3. PC의 타이밍 보정은 승인된 장면 연출에 음성 길이를 연결하는 작업이다. 장면 내용·디자인·팝업 구조·애니메이션 원본을 일방적으로 바꾸는 권한이 아니다. 출력물은 별도 버전 경로에 남긴다.
4. 유튜브는 검수된 해당 MP4를 비공개로 올리고 영상 ID·언어·파일 해시·실제 상태를 기록한다. 사용자 최종 승인 전 Public 전환·예약 공개를 하지 않는다. 계정 인증·비용·업로드 권한 및 기존 검수 조건도 확인한다.
5. 양쪽 기존 파일과 미커밋 작업을 먼저 보존한다. 승인 없이 상대 담당 파일을 수정·삭제·이동·복원·덮어쓰기하거나 통합·배포하지 않는다. 강제 푸시를 금지하며 GitHub 통합과 운영 반영은 사용자 승인 후 진행한다.
6. 맥북의 미커밋·미푸시 작업은 GitHub 다운로드만으로 확보되지 않는다. 확보 범위와 누락을 기록하고 확인 전 전체 통합 완료라고 보고하지 않는다. 일상 제작은 승인 버전과 변경분을 전달하며 매번 양쪽 전체 폴더를 합치지 않는다.

이 업무 분담은 2026-10-14 사용자의 “영어음성 생성 맥북담당이야”, “여기서 담당하는거야”, “지침도 수정해”에 따른 최상위 규칙이다. 이전 v3.2.1의 영어 PC 음성·싱크 담당 문구보다 우선한다. 이전의 ‘PC가 원본 장면 연출·애니메이션을 담당’ 또는 포괄 배포 허용 문구보다 우선한다. 지침 반영은 자동 연동·실제 영상 제작·업로드 기능의 완료 증거가 아니다. 맥북이 실제로 읽었는지도 별도로 확인한다.

| 순서 | 읽을 자료 | 확인할 내용 |
|---|---|---|
| 1 | 루트 `AGENTS.md` → 이 문서 전체 | 시작 규칙과 제작 순서 |
| 2 | `MASTER/IMPLEMENTATION_STATUS.md` | 실제 구현 범위와 알려진 한계 |
| 3 | `MASTER/INDEX.md` | 전문 지침 담당 영역 |
| 4 | `STORIES/<id>/PRODUCTION_NOTES.md` | 대상·현재 단계·미완료·다음 작업 |
| 5 | 대상 작품 `STORY_RULES.md`와 확정 대본 | 유지할 문장·장면 순서·그림·배역·구도 |
| 6 | 현재 변경 영역의 전문 문서 | 작업 방법과 검사 기준 |

새 작품에는 아직 4·5번 파일이 없으므로 `MASTER/PRODUCTION_RECORD_TEMPLATE.md` 양식으로 만든다. 재개할 때는 기존 기록을 갱신한다. 옛 완료 표시를 현재 버전으로 옮기지 않는다. 웹 수정 요청의 실행·검수·GitHub·영속 보고 순서는 [WEB_CONTROL](../DEPLOYMENT/WEB_CONTROL.md)을 따른다. 커밋·푸시·기록·배포·사용자 승인은 각각 판정한다.

아래처럼 시작을 알리고 실제 작업을 진행한다.

> 대상: [작품 ID·제목]. 현재: [단계·상태]. 이번에는 [결과물]까지 진행합니다. [확정 사항]을 유지하고, [확인 방법]으로 검수하겠습니다.

읽은 문서 경로·버전·적용할 핵심 규칙 3개를 작품 기록에 남긴다. 기록만으로 실제 독서나 검수가 증명되지는 않는다. 결과와 함께 대조한다.

## 3. 지시를 적용하는 기준

1. 사용자 최신 명시적 지시와 이미 받은 승인 범위를 먼저 확인한다. 어떤 기존 결정을 바꾸는 요청인지 구체적으로 기록한다.
2. 작품별 확정 사항은 `STORY_RULES.md`를 따른다. 요나의 배역이나 노아의 소품 수를 다른 작품에 옮기지 않는다.
3. 나머지는 이 문서의 절차와 전문 지침을 따른다. 현재 코드 수치나 오래된 상태 문구가 사용자 결정보다 우선하지 않는다.
4. 기존 제작지침과 충돌하는 내용은 임의로 결정하지 않고 기존 문구·새 요구·영향 범위를 보고한다. 이번 요청이 명시한 순서·승인 조건만 해당 항목에 통합하고, 새 요구로 판단할 수 없는 선택은 확인 대기로 남긴다.
5. `archive/`, `history/`, `USER_BRIEF.md`, 과거 보고서는 이력이다. 반려된 그림이나 폐기된 음성 설정을 되살리는 근거로 쓰지 않는다.

2026-10-17 웹 지침 전수 대조에서 이전 실행 순서·영어 로고/타이틀 변경 문구를 최신 언어별 순서·원화 재사용 기준에 맞게 정리했다. PC 사본의 실제 반영은 별도 대조·수신 확인 대상이다. 기존 기술 설정과 검수 기준은 유지한다.

지침 정리를 요청받았다면 지침을 정리한다. 동화 대본·원화·음성·엔진까지 함께 바꾸는 권한으로 확대하지 않는다.

## 4. 단계 상태와 통과 규칙

제작 완료와 MP4 제작 인계 전에는 [디자인·애니메이션 공통 기준의 「최종 품질 검수 및 반복 개선」](DESIGN_ANIMATION_PROTOCOL.md)을 필수 적용한다. 세부 기준은 해당 원문에서만 관리한다.

상태는 **미착수 / 진행 중 / 확인 대기 / 수정 필요 / 실패 / 통과 / 해당 없음** 중 하나다. 확인 대기에는 사용자 결정·파일 미확보·접근 불가 등 이유를 적는다.

- 단계 상태와 근거는 ko/en을 분리해 기록한다. 한 언어의 승인을 다른 언어의 대본·음성·출력 승인으로 간주하지 않는다. 두 언어의 최종 출력 검수 전에는 작품 전체 제작 완료로 보고하지 않는다. 통과에는 실제 결과물 경로, 확인한 버전, 검수 방법·결과가 필요하다. 사용자 확인이 필요한 항목은 확인 근거도 남긴다.
- 대본·대표 디자인·배역 등 이미 받은 승인은 다시 묻지 않는다. 새 선택이나 확정 사항 변경만 비교 가능한 결과를 먼저 만들어 확인받는다.
- 앞 단계의 필수 조건이 미완료면 그 결과에 의존하는 다음 단계로 넘어가지 않는다. 자료 정리·부품 목록 등 되돌리기 쉬운 준비는 계속할 수 있다.
- 음성 없이 만든 움직임·무음 영상은 **임시 검수본**이다. 전체 연기·싱크 단계의 통과로 기록하지 않는다.
- 기존 작품은 00 점검 후 변경이 영향을 주는 가장 이른 단계로 돌아간다. 유효한 승인까지 지우고 처음부터 다시 만들지 않는다.
- 10~12 공개 게시는 범위 밖이면 `해당 없음 — 이번 요청은 MP4까지`로 적는다. 13의 실제 GitHub/웹 상태 확인과 14 인수인계는 이번 범위에 맞게 수행하며, 보류·문서 수정 때도 실패·미확인 상태를 기록한다.
- 자동 검수 통과를 사용자 최종 승인으로 간주하지 않는다. 한국어·영어의 검수·최종 승인·공개 승인은 각각 독립적으로 기록한다. 승인 이후 영상 변경은 재검수·재승인 대상이다.
- 실패한 작업은 완료 또는 통과로 기록하지 않는다. 자동 제작 절차는 추가 유료 호출·크레딧 구매·AI 차단 해제를 허가하지 않는다.

## 5. 전체 제작 순서

먼저 지침 전체 검수 → 담당 문서 보완·버전업 → 실제 제작·배포·자동화 검증 순서로 수행한다. 아래 00~14 번호와 전문 기준은 보존하되 언어별 실행 순서는 다음과 같다. 한국어는 00→01-A/B 대본·장면 확정→01-C 음성 요청·PC 회신→01-D 연결·싱크→02 전체 검수→03 완성 확정→13의 Git/웹/완료 송신→PC 수신 확인→06→07→비공개 업로드·기록, 그 결과 확인 후 영어는 04의 웹 검토본 반영·대본 검수·사용자 승인→맥북의 이 대화에서 영어 음성 생성·실측→05 맥북 웹 연결·싱크·검수→13의 Git/웹/완료 송신→PC 수신 확인→06→07→비공개 업로드·기록으로 진행한다. PC에 맡긴 한국어의 완성 전 음성 요청은 HANDOFF의 audio.requested, 영어는 HANDOFF의 맥북 직접 제작 기록을 사용하며, 완성 후 제작 전달은 content.completed로 구분한다. 음성 요청에 한국어 전체 완성이나 완성본 배포를 선행 조건으로 요구하지 않는다. 언어별 필수 검수가 충족되지 않으면 해당 경로를 멈춘다. 08~12의 최종 영상 승인·Public 조건은 보존하며 이번 비공개 자동화 요청에서는 Public을 실행하지 않는다. 13~14 기록은 각 단계에서 갱신한다. 한국어 완성 확정 전에 영어 대본·음성 자동 제작을 시작하지 않는다. 실제 지원 여부와 승인된 실행 범위는 IMPLEMENTATION_STATUS.md에서 확인한다. 절차를 문서화한 것은 기능 구현·자동 실행 허가·사용자 승인이 아니다.

기존 대본·대표 장면·실제 음성·전체 싱크의 상세 기준은 01의 하위 순서로 보존한다. 기존 기록의 v2.x 단계번호를 새 번호로 자동 해석하지 않으며 [변경 대조](GUIDELINE_HISTORY.md)로 연결한다.

**할 일**

1. 실제 폴더 `bible-paper-studio`와 대상 작품 ID를 확인한다. 같은 이름의 초안·작품 폴더가 있으면 실제 연결을 확인한다.

3. 필요한 파일이 실제로 있는지 확인한다. 경량 ZIP에 PNG·MP3·MP4·런타임 자원이 빠졌다면 재생·시각 검수를 했다고 말하지 않는다.
4. 제작·수정 작업에서는 기존 제작실 탭을 재사용한다. 서버·포트를 확인하고 필요할 때만 `npm run dev`를 실행한다. 기본 주소는 `http://127.0.0.1:5180/dashboard#work`다.
5. 새 작품은 동일 ID가 없는지 확인한 뒤 생성한다. 폴더 생성과 작품 완성을 구분한다. 명령은 `STORY_TEMPLATE.md`를 따른다.

**남길 결과**: 기본 정보, 읽은 문서, 유지할 결정, 단계표, 이번 범위.

**통과 조건**: 대상·범위·접근 가능한 파일이 분명하다. 필요한 미리보기의 실제 접속을 확인했다. 문서 검토만 했다면 재생 미실시를 적었다.

## 01. 한국어 동화 제작 및 수정

아래 A→B→C→D의 기존 제작 기준을 한국어에 먼저 적용한다. 대표 동작은 B에서 임시로 시험하고 **전체 동작의 최종 시간은 C의 실제 음성으로 D에서 맞춘다.** 임시 초 단위 값을 음성 실측값이라고 쓰지 않는다.

### A. 대본과 장면표 확정

**할 일**

1. 성경 책·장·절, 대상, 핵심 메시지를 정한다. 본문 사건과 어린이용 재서술·연출을 구분한다.
2. 나레이션·대사를 쉽고 구체적으로 쓴다. ‘큰 발 뒤에 작은 발’ 같은 모호한 표현, 같은 말의 불필요한 반복을 피한다.
3. 발화마다 고유 ID와 화자를 붙인다. 기존 한국어 문장 원본은 `story.json`이며 한국어 대본을 먼저 확정한다. 영어 대본은 한국어 전체 제작·검수와 03 완성 확정 후 04에서 맥북이 제작·검토한다. 언어별 원본·장면 ID 대응·이름 표기는 `STORY_GUIDE.md`를 따른다. 읽기용 대본·녹음용 문서·SRT도 대조한다.
4. 장면표에 **장면 번호 / 펼침면 / 발화 ID / 나레이션·대사 / 보이는 종이 / 시작·핵심·종료 동작 / 다음 전환**을 연결한다.
5. 이야기의 ‘장면’과 물리적 ‘펼침면’을 구분한다. 같은 면의 연속 행동마다 책장을 넘기지 않는다. 사용자가 정한 19장면을 구현 편의로 9장면으로 줄이지 않는다.
6. 누가 어느 쪽에서 출발하고, 어떤 종이 부품이 움직이며, 어디에서 끝나고 무엇에 가려지는지 적는다. 카메라 연출로 해결하지 않는다.
7. 대본·순서를 사용자 지시와 대조한다. 제안과 확정본을 구분한다. 이미 확정된 대본을 다시 창작하지 않는다.

**남길 결과**: 한국어 확정 대본·장면표·인물명·지명 표기/발음표·본문 검토 근거. 양언어 발화 대응표와 영어 번역 검토 근거는 04에서 완성한다.

**통과 조건**: 요구된 장면·대사가 빠짐없이 맞는 순서로 대응한다. 미확정 문장을 몰래 채우지 않았으며 대본 확인 범위가 기록됐다.

상세: `STORY_GUIDE.md`, `STORY_TEMPLATE.md`.

### B. 대표 장면으로 그림과 구조 확인

**할 일**

1. 승인된 참고 원화를 실제로 열어 본다. 파일명이나 프롬프트만 읽고 같은 스타일이라고 판단하지 않는다.
2. 대표 1장면을 책 위에 배치한다. 주인공·소품·배경·자막을 함께 확인할 수 있게 만든다.
3. 종이 섬유·얇은 단면·오린 형태·앞뒤 겹침을 유지한다. 흐림이나 깨진 경계를 ‘거친 종이 느낌’으로 설명하지 않는다.
4. 앞뒤 모습과 필요한 팔·몸 자세를 확인한다. 어려운 자세는 필요한 원화·부품을 준비한다.
5. 짧은 접힘·펼침과 대표 동작을 시험한다. 임시 시간표라고 표시하고 실제 화면이나 짧은 검수 영상을 보여준다.
6. 확인된 원화 경로·버전·화면을 `STORY_RULES.md`에 기록한다. 승인받지 않은 새 스타일로 전체를 대량 제작하지 않는다.

**남길 결과**: 대표 장면, 원화 목록, 앞뒤·중간 자세·전환 검수, 디자인 확인 근거.

**통과 조건**: 스타일·가독성·종이 구조가 확인되고 유지할 기준이 실제 파일로 남아 있다.

상세: `DESIGN_SYSTEM.md`, `ANIMATION_GUIDE.md`의 구조 항목.

### C. 실제 한국어 음성 준비

이미 완료한 음성은 HANDOFF의 보존·철회 규칙에 따라 기존 파일을 확보한다. 아래 요청·생성 경로는 승인된 신규 음성 작업에만 적용한다. 이번 요나 한국어는 사용자가 맥에서 완료했다고 확정했으므로 PC 재생성 없이 기존 음성과 타임라인을 전달한다.

**할 일**

1. 한국어 내레이터 나윤·하나님 권일의 시리즈 배역을 유지한다. 영어 배역은 영어 실제 샘플로 별도 선정한다. 새 인물은 실제 샘플로 정한다. 요나의 현준을 노아나 다윗에 자동 배정하지 않는다.
2. 확정 대본으로 녹음용 목록을 만든다. 샘플 확인·이미 승인된 비용 범위·실제 제작 경로를 확인한다. MAC은 [HANDOFF의 완성 전 음성 요청·회신](HANDOFF.md)에 따라 변경·누락 발화와 재사용 후보를 구분해 요청하고, PC는 실제 음성과 검사 근거를 회신한다. 기존 요청 접수나 완료 표시는 현재 전체 음성·작품 검수 통과와 구분한다.
3. 실제 MP3와 대응 SRT를 확보한다. 접근이나 파일이 없으면 필요한 자료를 정확히 알린다. 브라우저 음성·무음을 최종 음성으로 대신하지 않는다.
4. 회신 연결 직전에 최신 저장 revision/해시와 발화별 문장·화자·배역을 재대조한다. 지정 담당자가 문장 수·문구·화자·순서·시간을 확인해 가져오고 원본과 문장별 파일·실측 길이·배역 정보를 보존한다. 늦은 회신으로 최신 대본·사용자 타이밍·배치를 덮어쓰지 않는다.
5. 모든 발화의 발음·어미·감정·음량·끝 음절을 듣는다. 길이 측정과 청취를 구분한다.

**남길 결과**: 한국어 배역·원본 MP3/SRT·장면/발화별 manifest·실측/청취 기록. 같은 음성 검수 기준은 04 영어 자동 제작 결과에도 적용한다. 서비스 연결·생성 실패는 원인과 미완료 발화를 기록한다.

**통과 조건**: 실제 음성이 모두 있고 확정 문장과 일치한다. 문장·성우 변경으로 낡은 음성이 섞이지 않았다.

상세: `AUDIO_GUIDE.md`. 실제 음성이 없으면 해당 언어의 최종 싱크 통과는 보류한다.

### D. 전체 제작과 한국어 싱크

아래 양언어 공통 기준을 한국어에 먼저 적용하고, 영어 제작 이후 05에서 다시 적용한다.

**할 일**

1. 장면표 순서대로 `원화 → 배치 → 연기 → 음성·자막 → 전환 → 실제 재생 확인`을 마친다.
2. 각 언어의 실제 음성 길이로 별도 타임라인을 만들며 전체 길이는 달라도 된다. 언어 전환은 화면 글자·음성·자막·동작 시점·책장 넘김 시간을 함께 전환해야 한다. 실제 음성의 핵심 단어·문장 경계에 등장·걷기·손 내밀기·문 닫힘을 연결한다. 문장 길이 비율만으로 적당히 맞추지 않는다.
3. **마지막 음성, 자막 읽기 시간, 필요한 동작이 모두 끝난 뒤 감상 여유를 두고 다음으로 간다.** 음성이 끝나도 비둘기가 돌아오는 중이면 전환하지 않는다. 페이지 전환 중 이전 대사가 잘리거나 다음 장면 음성이 먼저 시작하지 않도록 한다.
4. 펼침면이 바뀌면 페이지 회전과 종이 접힘·펼침을 같은 진행값에 연결한다. 종이를 먼저 감추고 빈 페이지를 넘긴 뒤 새 그림을 띄우지 않는다.
5. 같은 면은 계획된 연속 행동·가림·종이 부품 교체로 이어간다. 장면 번호가 바뀌었다고 책 전체를 닫지 않는다.

**통과 조건**: 해당 최종 파일에 대한 실제 사용자 검수 근거가 있다. 최종 승인과 공개 클릭은 다음 단계에서 별도로 기록한다.

## 09. 한국어·영어 각각 최종 승인

1. 한국어와 영어 각각 언어·영상 버전·MP4 SHA256에 대응하는 사용자 최종 승인과 공개 승인 범위를 명시적으로 기록한다. 한 언어 승인을 다른 언어에 적용하지 않는다.
2. 자동 검사·제작자 자체 검수·기존 approve 명령·과거 파일명 final을 사용자 승인으로 간주하지 않는다. 이미 유효한 동일 파일 승인만 보존한다.
3. 승인 후 영상이 바뀌면 영향받는 언어의 승인을 수정 필요로 표시하고 07 자동 재검수 → 08 사용자 재검수 → 09 재승인을 거친다. 공통 변경이면 두 언어를 대조한다.

**통과 조건**: 공개하려는 각 언어의 현재 최종 파일과 승인 근거가 일치한다. 한 언어만 승인된 상태를 양언어 최종 승인 완료로 기록하지 않는다.

## 10. 사용자가 [유튜브 공개 게시] 버튼 클릭

1. 공개 대상 채널·작품·언어·최종 영상/버전과 언어별 승인 상태를 사용자에게 표시한다. 승인되지 않았거나 승인 이후 바뀐 파일은 공개 대상에서 제외한다.
2. 사용자가 **[유튜브 공개 게시]** 버튼을 직접 클릭해야 공개를 진행한다. 대화의 일반 제작 요청, 자동 검수 통과, 최종 영상 승인만으로 공개를 자동 시작하지 않는다.
3. 클릭의 주체·시각·대상 언어/영상·승인 버전·공개 설정을 기록한다. 에이전트나 자동화가 사용자 대신 버튼을 누르거나 클릭 기록을 만들지 않는다.
4. 해당 버튼과 승인 검증 연결이 없으면 현재 미구현/확인 대기로 표시하고 11을 진행하지 않는다. 문서에 버튼 이름이 있다는 이유로 실제 기능이 있다고 보고하지 않는다.

**통과 조건**: 현재 승인본을 대상으로 한 실제 사용자 클릭 근거가 있다.

## 11. 승인된 영상만 유튜브 Public 공개

1. 언어별 제목·설명·성경 범위·AI 음성 안내·실제 장면 썸네일·자막을 준비한다. 초기 한 채널·언어별 별도 영상과 재생목록 운영은 SERIES_GUIDE.md를 따른다.
2. 계정·채널·현재 정책·사용권·설정을 확인한다. 과거 설명을 현재 서비스 상태로 단정하지 않는다.
3. 비공개 업로드는 07 이후 해당 언어의 필수 영상·음성·자막 검수와 기존 권한 조건을 통과하면 PC가 독립 처리한다. 10의 Public 클릭을 비공개 업로드의 선행 조건으로 삼지 않는다. 영상 ID·언어·MP4 해시·실제 private 상태와 처리 완료 여부를 기록하며 Public 완료로 표시하지 않는다.
4. 09의 언어별 승인, 10의 실제 사용자 클릭, 현재 검수 fingerprint·렌더 보고서·MP4 SHA256·대상 영상 ID가 모두 일치하는 영상만 YouTube Public으로 전환한다. 사용자 승인 없이 공개하지 않는다.
5. 실패·중단된 작업을 완료로 기록하거나 신규 업로드/재공개로 중복 처리하지 않는다. 기존 영상 ID·실패 원인을 보존하고 실제 상태를 확인한다.

MP4까지만 요청된 경우 게시하지 않는다. 기존 공개/예약 CLI는 기술 지원 경로로 보존하지만 이 제작 흐름의 승인·버튼 조건을 대신하지 않는다. 예약 게시로 Public 공개 완료를 대체하지 않으며 별도 예약 요청의 충돌은 보고한다. 상세: SERIES_GUIDE.md, YOUTUBE_AUTOMATION.md.

## 12. 실제 공개 상태 및 URL 확인

1. ko/en 각각 실제 YouTube 영상 ID·채널·URL·공개 상태와 확인 시각을 조회·대조한다. 요청 성공 응답이나 URL 문자열만으로 Public이라고 판단하지 않는다.
2. 비공개·일부공개·예약·처리 중·제한·접근 불가이면 그대로 기록한다. 실제 public 상태와 해당 URL의 공개 재생 가능 여부가 확인되지 않으면 공개 완료로 표시하지 않는다.
3. 확인 실패는 원인과 필요한 조치를 남기고, 공개 완료를 전제로 하는 최종 보고를 하지 않는다. 승인되지 않은 다른 영상을 대신 공개하지 않는다.

**남길 결과**: 언어별 영상 ID·실제 public 상태·URL·확인 근거. **통과 조건**: 요청된 각 영상의 실제 공개 결과가 확인됐다.

## 13. GitHub·웹 배포 상태 확인 및 제작 이력 기록

1. GitHub의 대상 저장소·브랜치·로컬 커밋/미커밋 상태와 원격 SHA·push 결과를 대조한다. 로컬 저장/커밋만으로 GitHub 반영 완료라고 하지 않는다. 기존 사용자 수정과 작업 중 변경은 보존한다.
2. 웹 배포 저장소의 소스 SHA·저장 버전·배포 ID·실제 성공 상태·URL·인증 범위를 별도로 확인한다. GitHub push, Sites source push, 웹 배포, YouTube Public은 서로 다른 결과다. 비공개 웹 제작소의 접근 설정을 YouTube 공개와 함께 바꾸지 않는다.
3. PRODUCTION_NOTES.md와 기록 양식에 ko/en 기준 버전·MP4/SRT 해시·자동 검수·사용자 검수/승인·공개 클릭·실제 URL·GitHub/웹 상태·실패 원인과 재시도 결과를 남긴다. 키·토큰·인증 파일을 기록에 포함하지 않는다.
4. GitHub 커밋 전에 파일별 MAC/PC/공유 담당, 변경 이유, 이번 승인 근거를 목록으로 확정한다. MAC 파일과 이번 요청으로 지정된 지침만 명시적으로 stage한다. fetch 후 기준 SHA와 원격 변경을 대조하고 겹치는 파일이 있으면 해당 담당에게 돌린다. MAC 작업 브랜치 codex/*에 일반 push하며 master 병합·강제 push·상대 변경 삭제는 하지 않는다.
5. 현재 Sites 소스 브랜치와 GitHub 작업 브랜치는 별개다. 승인된 변경만 최신 Sites 소스에 적용하고 미리보기 전용 범위·기존 접근 설정을 유지한다. 배포 직전 원격 SHA를 재확인하고 바뀌었으면 재검수한다. 소스 commit·배포 버전/ID·GitHub commit의 대응을 기록한다. 실제 URL에서 해당 언어의 전체 재생·전환 중간·음성/자막·모바일 가독성을 확인한다.
6. 01-C의 PC 사전 음성 요청·회신과 04의 맥북 영어 직접 제작은 해당 제작 단계에서 처리하며 완성본 송신 대기로 묶지 않는다. 배포 검수까지 통과한 입력에만 HANDOFF의 content.completed 이벤트를 MAC에서 작성·송신한다. 원격 Git SHA 확인과 PC 수신 ACK는 별개다. ACK·MP4·private 업로드의 실제 증거가 없으면 각각 미확인이다.
7. 필요한 동기화·배포가 실패/미실행/확인 대기이면 이유와 남은 작업을 명시한다. 현재 작업 범위에 포함되지 않은 게시를 자동 실행하지 않는다. 원격 확인 불가를 성공으로 바꾸지 않는다.

**통과 조건**: 실제 결과와 제작 이력이 일치하고, 필요한 GitHub/웹 반영이 확인됐다.

## 14. 최종 완료 보고

1. `PRODUCTION_NOTES.md`의 해당 항목을 갱신한다. 날짜별 공지를 계속 붙이지 않는다.
2. ko/en 각각 완료 범위·증거·미확인·다음 한 단계를 경로·시각과 함께 남긴다. 영상 제작 완료와 게시 완료를 구분한다.
3. 결정이 바뀌면 `STORY_RULES.md`를 수정하고 변경 이유·이전 값은 이력으로 옮긴다.
4. 공통 문서를 수정했으면 표시본을 동기화한다. 열어둔 제작실은 확인 가능한 상태로 유지한다. 환경 종료 후에도 서버가 계속 실행된다고 보장하지 않는다.
5. 실제 결과물과 함께 짧게 보고한다. 이번에 확인한 범위와 남은 일을 정확히 말한다.
6. 한국어·영어 각각 최종 파일·SHA256, 자동/사용자 검수, 최종 승인, 실제 공개 URL, GitHub 커밋과 웹 배포 버전/상태를 함께 보고한다. 실패한 작업은 실패, 미실행/미확인은 그대로 표시한다. 요청된 필수 단계가 남으면 전체 최종 완료라고 보고하지 않는다.
7. 문서 수정·부분 제작·보류로 끝나는 작업도 이 인수인계를 수행한다. 게시 범위 밖인 단계는 이유를 붙여 해당 없음으로 남기고 이번 요청의 완료 범위만 보고한다.

상세: `HANDOFF.md`, `PRODUCTION_RECORD_TEMPLATE.md`.

## 6. 중간 수정 요청을 받았을 때

| 바뀐 내용 | 돌아갈 단계 | 다시 확인할 항목 |
|---|---|---|
| 문장·장면·순서 | 01 | 해당 음성·자막·연기·전환·전체 길이·출력 |
| 그림·인물 비율·소품·구도 | 01-B | 연결부·가림·접힘·가독성·출력 구도 |
| 배역·발음·녹음 | 01-C / 04 | 실측 길이·읽기 시간·동작·자막·믹스·출력 |
| 동작·시간·페이지 전환 | 01-D / 05 | 앞뒤 연결·음성/자막 종료·탐색·출력 |
| 렌더러·CSS·화면 비율 | 06 | 미리보기 비교·MP4 재출력/비교 |
| 게시 제목·설명·설정만 | 10~12 | 게시 정보·결과; 영상이 같으면 재출력 불필요 |

영향받는 통과 표시는 `수정 필요`로 바꾼다. 관계없는 장면의 승인까지 폐기하지 않는다. 다만 최종 영상 파일이 변경되면 영향받은 언어의 07~09 재검수·재승인을 거치고 새 파일의 10 공개 클릭 근거를 다시 확보한다. ‘느리다’가 대사 뒤 대기 문제면 문장을 삭제하지 않고 대기 시간을 고친다.

## 7. 규칙을 바꾸는 순서

**요청 분류 → 원문·기존 변경 보존 → 충돌 보고 → 담당 문서의 실제 제작 위치에 통합 → 변경 전후 누락·중복·충돌 대조 → 변경 이력 → 표시본 갱신·실제 참조 경로 검증** 순서로 처리한다.

공통 규칙은 전문 지침에, 작품별 결정은 `STORY_RULES.md`에, 미완료·오류는 `PRODUCTION_NOTES.md`에 기록한다. 새 `최종_최신_추가` 문서를 계속 만들거나 여러 문서에 같은 규칙을 복제하지 않는다.

기존 규칙은 임의로 삭제하거나 변경하지 않는다. 새 요청으로 바뀐 적용 시점·승인 조건과 보존한 품질 기준은 GUIDELINE_HISTORY.md에 기록한다.

준수 여부는 읽었다는 말이 아니라 **정해진 순서의 결과물과 검수 기록이 실제로 남아 있는가**로 판단한다.
